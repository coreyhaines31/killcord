## 1. Swift worker on Linux

**Answer: yes, on macOS and on Linux.** In CI run 44217878541 on Linux, `swift build`, `swift test` (8 tests in 2 suites, all passing, the database tests included: w1 102, w2 97, w3 102, w4 99 rows) and `swift run killcord-worker-spike` all exited 0.

Toolchain finding: the resolved dependencies (`swift-collections` 1.7.6, and `swift-log`, `swift-nio` siblings at tools 6.2) need Swift 6.2 to 6.4 tools. The first CI run with `setup-swift` 6.1 failed to resolve them. The worker image should build on `swift:6.4.2-noble` or newer, and KillCordCore's own CI (Swift 6.1) is unaffected because it has no dependencies.

What exists, in `spikes/teams-worker/` (a separate SwiftPM package, outside the app and outside the shipped KillCordCore):

- `Envelope.swift`: AES-256-GCM with a fresh data key per stored key. The data key is wrapped by the org's key, and both layers authenticate the encryption context `{org_id, connection_id}`. `LocalKeyService` is the local stand-in for KMS behind two protocols that the AWS client will implement: `DataKeyWrapping` (`kms:Encrypt`, the web app's only power) and `DataKeyUnwrapping` (`kms:Decrypt`, the worker's). The wrapped blob names its key, as a KMS ciphertext blob does. Crypto comes from `swift-crypto` 4.5.2, which works on Linux.
- `Worker.swift`: one `UPDATE ... WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED) RETURNING` statement leases due rows and sets `lease_owner` and `lease_until`. The worker decrypts in memory, decodes `ProviderCredentials`, calls KillCordCore's real `OpenAIProvider` through a `MockHTTPClient`, writes a `spend_readings` row, and releases the lease with the next poll time. A decrypt failure releases the lease and records `last_error`, without calling the provider. Postgres access is `postgres-nio` 1.33.3. The worker connects as the `kc_spike_worker` role from section 2.
- `killcord-worker-spike`: an executable that drains once against the database. It ran: `killcord-worker-spike: 0 connections handled`, exit 0.

Evidence (macOS, local database, `KC_SPIKE_PGHOST=localhost swift test`, exit 0, 8 tests in 2 suites):

| Proof | Result |
|---|---|
| Two workers never take the same row (`concurrentWorkersNeverTakeTheSameRow`) | Four workers, each with its own connection pool, drained 400 due connections across 5 orgs in batches of 3. 400 readings, 400 distinct connections, every provider request carried the decrypted fake key and was a GET to `api.openai.com`. Split: w1 99, w2 100, w3 99, w4 102 |
| The test can fail | With `FOR UPDATE SKIP LOCKED` removed, the same test failed three runs out of three: 457 to 468 polls for 400 rows (`polledIDs.count == ids.count` and `readings.count == ids.count` failed). Reverted afterwards |
| A ciphertext copied to another org fails (`aCiphertextCopiedToAnotherOrgFailsToDecrypt`) | Org 0's sealed key copied onto org 1's row, and onto a new row in org 0: both `failed("cannot decrypt ...")`, and the mock provider was called exactly once, for the untouched row |
| Envelope unit tests (no database) | Round trip; another org fails; another connection fails; a swapped data key fails; a missing org key fails; the context has the KMS map shape |
| SwiftLint | `swiftlint lint --strict` with the repo's rules: 0 violations |

What the spike does not prove: TLS to the database (it used `tls: .disable` locally; Neon requires TLS and `postgres-nio` supports it, untested), real KMS behavior (section 5), the outbound host allowlist (I9), and anything under load beyond 400 rows.

## 2. Postgres roles, column grants and row-level security

### 2a. Local Postgres: yes

`spikes/teams-worker/sql/schema.sql`, `roles.sql`, and `check-roles.sh` (exit 0 only when every check behaves). Run on Postgres.app 15.17 and in CI on Postgres 17. **16 passed, 0 failed** on both:

- **Web role (`kc_spike_web`):**
  - Sees only the org set with `app.org_id`, and nothing when it is unset.
  - Gets `permission denied` for `SELECT key_ciphertext`, for `SELECT *`, and for `UPDATE ... RETURNING key_ciphertext`.
  - Can still replace its own org's key (write-only).
  - Is stopped by RLS when it inserts into another org, and its update of another org's key changes 0 rows.
- **Worker role (`kc_spike_worker`):**
  - Gets `permission denied` on `users`, `sessions` and `orgs`.
  - Reads ciphertext for every org.
  - Cannot rewrite a stored key or delete connections.
  - Can take a lease with `FOR UPDATE SKIP LOCKED`.

Two design findings for unit 4:

- **Prisma reads every scalar column by default**, so a web role with a column-level REVOKE breaks any Prisma query on `connections` that doesn't list its fields. Put the ciphertext in its own 1:1 table (`connection_keys`) that the web role can INSERT, UPDATE and DELETE but never SELECT. A missing `select` then fails loudly instead of leaking.
- **RLS with a pooled connection** needs `SET LOCAL app.org_id` inside the same transaction as the query (a Prisma interactive transaction). A plain `SET` leaks to the next request on that connection. The policy core should open that transaction for every org-scoped request.

### 2b. Prisma Postgres: no. Fallback: Neon

From the [Prisma FAQ, "Can I create my own database roles?"](https://www.prisma.io/docs/more/faq#can-i-create-my-own-database-roles), read November 17, 2026:

- "Prisma Postgres doesn't support custom roles."
- "The database user in your connection string can't create roles, so `CREATE ROLE` fails with this error: `ERROR: restricted superuser cannot create roles`"
- "If you wanted a role to give one part of your application read-only access, enforce that in your application instead."

With one login, there is no second role to grant columns to, and RLS cannot separate the web app from the worker. Whether `CREATE POLICY` itself works there was not stated.

From Neon's [Manage roles](https://neon.com/docs/manage/roles) and [RLS guide](https://neon.com/docs/guides/row-level-security):

- "To create a role with SQL, issue a CREATE ROLE statement from a client such as psql, pgAdmin, or the Neon SQL Editor."
- SQL-created roles "are not granted membership in the neon_superuser role like roles created with the Neon Console, CLI, or API". They "must be selectively granted permissions for each database object."
- Console and API roles "are administrator roles with neon_superuser privileges", and in newer projects neon_superuser carries BYPASSRLS. **So the app and the worker must connect as SQL-created roles, never console roles.**
- RLS is documented, with `ENABLE ROW LEVEL SECURITY` and `CREATE POLICY` examples.
- Column-level GRANT is not mentioned on those pages. It is standard Postgres and section 2a proves the semantics, but it has not been run on Neon. Check it with `check-roles.sh` on a Neon branch when the database is created.

**Recommended fallback (Corey to confirm, since it departs from the default stack):** the Teams database is Neon, with SQL login roles `kc_web`, `kc_worker` and `kc_migrate` (owner, migrations only). Prisma ORM stays. This departs from the Prisma Postgres default for the reason quoted above.

## 3. Better Auth organization plugin

**Answer: yes for teams, invitations and many orgs per user. No native per-team manager.**

Read from the [organization plugin docs](https://www.better-auth.com/docs/plugins/organization) and the published package `better-auth@1.7.25` (npm latest on November 17, 2026, unpacked `dist`). No scratch app was built, so nothing here was exercised.

| Need | Supported | Evidence |
|---|---|---|
| Teams inside orgs | yes | "To enable teams, pass the `teams` configuration option to both server and client plugins." `maximumTeams`, `maximumMembersPerTeam` |
| A member in several teams | yes | `listUserTeams` (`routes/crud-team.mjs:448`). Invitations accept comma-separated team ids (`routes/crud-invites.mjs:297`) |
| Invite straight into a team | yes | "The invited member will be added to the specified team upon accepting the invitation." |
| Invitation expiry | yes | `invitationExpiresIn`, "By default, it's 48 hours (2 days)" (code default `172800` seconds, `adapter.mjs:738`). Set the spec's value explicitly |
| Many orgs per user, switching | yes | List orgs, `organization.setActive`. The session stores the active organization and active team |
| A finance role | yes | Custom roles through `createAccessControl`, or dynamic roles at runtime. `member.role` accepts several comma-separated roles (`roles.mjs:15`) |
| Per-team manager role | **no** | `teamMember` has only `id`, `teamId`, `userId`, `createdAt` (`schema.d.mts:289`), and its schema option takes no `additionalFields` (`types.d.mts:276`), unlike `member`, `invitation` and `team`. The docs say teams "follow the organization's permission system" |

**Gap and fix:** a `team_manager(team_id, user_id)` table of our own, read by the policy core. "A manager sees their own team only" can't be expressed in the plugin's permission checks either way, so that rule lives in the policy core and its negative tests (unit 2). A `team.managerUserId` additional field would limit a team to one manager, so it was not chosen.

## 4. Fuel Gauge machine-readable output

**Answer: yes.**

- **The CLI:** `/Applications/Fuel Gauge.app/Contents/MacOS/fuelgauge` (app 1.12.0, `CFBundleShortVersionString`), linked to `/opt/homebrew/bin/fuelgauge` by the cask. `fuelgauge --version` printed `1.12.0`.
- **Commands** (Fuel Gauge source, `FuelGaugeCLI/main.swift:4-35`): `status [--json]`, `resets [--json]`, `history [--json]`, `backtest [--json]`. `status` exits 2 when a limit is forecast to run out before its reset (`main.swift:103`).
- **JSON** (`Packages/FuelGaugeCore/Sources/FuelGaugeCore/ForecastJSON.swift:3-74`): an array with one object per limit, snake_case keys, ISO-8601 dates.
  - `tool`, `account`, `account_name`. The account fields are omitted for a tool's single default account.
  - `window`, `limit`, `model`.
  - **`used_percent`** and **`resets_at`**.
  - `verdict`, `runs_out_at` and other forecast fields, `last_reading_at`, `summary`.
- **Observed:** one `fuelgauge status --json` run on November 17 returned 4 limits for the claude, codex and grok-bot tools, each with `used_percent` and `resets_at`, and exited 2.
- **Side effects:** the CLI never writes Fuel Gauge's defaults (`Account.swift:173-184` only reads). `status` can append Grok Bot readings to Fuel Gauge's own `Readings` folder (`main.swift:67-68`), which is its normal behavior.

**For unit 15:** build the employee's share payload from `status --json`, keeping only `tool`, `window`, `limit`, `model`, `used_percent`, `resets_at` and `last_reading_at`. Drop `account_name` (it can be an email or a person's label), `summary`, and the forecast fields. One function builds both the preview and the payload (invariant I6). Whether Kill Cord shells out to an installed Fuel Gauge or reads the same sources itself is decided in unit 15.

## 5. Blocked on AWS (do in one sitting once #51 exists)

Account setup:

1. Account with MFA on root, an admin IAM Identity Center user, CloudTrail on in all regions, and a billing alarm. Ideally a dedicated account for Kill Cord Teams only, so "whoever administers the account can grant decrypt" (spec section 10) covers as few people as possible.
2. Check current KMS pricing on the AWS pricing page. A per-key monthly charge times one key per org matters against a roughly $10 Solo tier. If it doesn't fit, the fallback is one key per tier or region with the org id carried only in the encryption context. That needs a spec change, because "one key per org" also makes org deletion a key deletion (I10).

KMS:

3. Key creation path: a provisioning step (admin role, not the web app's runtime identity) that runs `CreateKey` with tag `org_id`, plus an alias, when an org starts its trial or pays.
4. Key policy per key:
   - The web role gets `kms:Encrypt` only.
   - The worker role gets `kms:Decrypt` only.
   - Both carry a condition that `kms:EncryptionContext:org_id` equals the key's org, so even a confused caller can't use org A's key with org B's context.
   - No human principal gets Decrypt.

Identities:

5. **Web app identity:** Vercel OIDC federation to an IAM role (`AssumeRoleWithWebIdentity`), so the web app holds no long-lived AWS key. Check that the current Vercel docs support it for the team's plan.
6. **Worker identity:** a task role on Fargate or App Runner (decision 2). Settle which, and the region.
7. **Worker egress:** a security group can't filter by hostname. The provider-host allowlist needs AWS Network Firewall domain lists or an egress proxy. Without them, egress is "any HTTPS" and I9's in-process allowlist is the only control. Decide which, and say so in the threat model.

Worker deployment:

8. Container: a `Dockerfile` (build on `swift:6.4.2-noble` or newer, run on the matching `-slim` image), an ECR repository, and the deploy pipeline from CI (GitHub OIDC to AWS, no stored keys).
9. AWS client in Swift: Soto's KMS module or a minimal SigV4 client implementing `DataKeyWrapping` and `DataKeyUnwrapping`. Not evaluated in this spike.
10. Database reachability: the worker connects to Neon over TLS as `kc_worker`. Untested.

Proofs that need the real thing (from the spec's invariants):

- **I2 (a):** the web identity calling `kms:Decrypt` gets AccessDenied.
- **I2 (c):** a port scan of the running worker task shows no listener.
- **I4:** a real KMS `Decrypt` with the wrong context fails (`InvalidCiphertextException`), and a key policy condition rejects the wrong org.
- **I10:** org deletion schedules key deletion.
